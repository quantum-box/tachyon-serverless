journal fsync latency (journal-ab/)
A/B on Firecracker with the warm pool, examples/hello, 1 priming + 40 sequential warm invokes per gateway,
order A1 B1 A2 B2 (summary.json, attempts.jsonl, gateway-*.toml):
  A = [store] backend "sqlite": state.db, usage/journal.db (WAL, synchronous = FULL, one BEGIN IMMEDIATE
      transaction per event) and logs/logs.db on the root ext4
  B = [store] backend "memory": the journal and the state are in-memory SQLite (no fsync); logs as well
Per warm invoke the journal appended 3 events (handler_started, handler_finished, attempt_settled; the
ledger of A1 and A2: 41 each, plus one environment_started / environment_stopped per gateway).

- The durable stores add about 7 ms to the host-measured platform time (p50 11-12 vs 4-5 ms, p95 16-17 vs
  6-7 ms) and about 19 ms to what the client sees beyond the handler (client - handler p50 26-30 vs 9 ms,
  p95 39-41 vs 12 ms): part of the durable writes (the attempt's settlement, the logs flush) happens after
  total_ms is stamped but before the HTTP response. B removes the fsyncs of state.db and logs.db too, so
  this is an upper bound of the journal's share, not the journal alone.
- Handler times drifted with the Mac's load (51 -> 108 ms p50 across the four runs, Mac load1 22 -> 50);
  the host-platform difference between A and B stayed the same in both pairs.
- Append microbenchmark (journal-append-bench.py, the same statements as journal.rs::append from python's
  sqlite3, 500 appends of a 1444-byte body):

    journal-append-bench-tmp-tmpfs.json: the first attempt ran on /tmp, which is tmpfs in this VM (fsync is a
