WHAT EXPLAINS THE DIFFERENCES (reading, with what supports it)
1. Host contention, not code, explains most of the cold / fresh / warm p95 improvements: the calibration loop
   was 4-5x slower before the old cpu-burn sample and the Mac peaked at 31.5; now it was flat (77-85 ms) with
   a lower peak (17.2). The boot time p50 is unchanged (5.1 s) and the throttling ratio is still 0.99, so the
   cold path did not get faster; its tail did.
2. Admission / autoscaler (PLT-4634) replaced the [capacity] semaphore: with the pool off and 8 clients the
   old run timed out 9 queued requests after 10 s (504 Host.QueueTimeout); the new admission queue kept the
   24 requests with queue p95 7.7-8.6 s (below queue_timeout_seconds = 10) and served all of them, so
   throughput rose from 0.41-0.42 to 0.51-0.55/s at the price of a higher p50 (the queue is paid by more
   requests instead of failing some). This is close to the 10 s limit on this host; a slower host would
   time out again.
3. Warm pool at c=8 (all warm, 14-70 req/s instead of 0.7-3.6): the environments pooled by the earlier sweep
   levels were reused; admission holds requests over the revision cap of 4 in the queue (queue p50 43-44 ms,
   cpu-burn 266 ms) instead of booting extra microVMs (old: 1-2 cold boots and 2 x 502
   Host.EnvironmentBootFailed in http-axum). Zero-scale (PLT-4635): gateway-warm.toml sets idle_ttl_seconds
   = 900, longer than the warm phase, so pooled environments were not reclaimed between levels.
4. Usage journal fsync (PLT-4642): not visible in the warm host platform (p50 5-6 ms vs 6-8 ms before). The
   A/B in docs/evidence/kvm-final-usage-budget-20260917T151250Z/journal-ab/ puts the durable stores at about
   +7 ms host platform and +19 ms client - handler at p50 on this host; in this run the gain from a quieter
   host is larger than that cost, so the two runs cannot isolate it.
5. Durable invocation logs writer (PR #36, logs.db) and the other durable stores (usage journal / ledger,
   budget store, config cache loops): the gateway's fixed RSS grew by about 11 MiB and its idle CPU from
   3 to 16-18 ticks per 60 s (flush every 200 ms, collector every 1 s, admission/scaling reconcile). This is
   the new idle cost of the gateway process, not of the environments. Not decomposed per component: the
   attribution to these loops is a reading of what main added since 3704c80, not a measurement.
6. Budget is off by default (no [budget] section in config/gateway.firecracker.toml; /readyz budget.enabled
   false in the KVM runs of this batch), so no budget
   reservation is in these numbers.

LIMITS    one run each; nested virtualization on a shared Mac; not x86_64 / bare metal; see docs/benchmark.md §7.
